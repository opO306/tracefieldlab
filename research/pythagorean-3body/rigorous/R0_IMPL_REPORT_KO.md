## 1. 쉬운 설명
- 이 부품은 "계산 결과는 반드시 이 두 수 사이에 있다"를 지키는 계산기다. 숫자 하나 대신 **구간 [하한, 상한]** 을 들고 다닌다.
- 비유(실제와 구분): 자로 잴 때 눈금 사이에 걸리면, 하한은 **아래 눈금**, 상한은 **위 눈금**으로 적는다. 절대 안쪽으로 깎지 않는다. 그러면 진짜 값은 늘 두 눈금 사이에 있다.
- 실제 구현: 끝점을 "정수 가수 × 2^지수"로 저장하고, 가수는 최대 `get_prec()`(기본 128)비트다. 계산 결과의 정확한 값을 정수로 구한 뒤, **하한은 내림, 상한은 올림**을 *한 번만* 한다. 여러 번 반올림하지 않으니 불필요하게 넓어지지 않는다.
- 이 구현은 **증명이 아니라 구현 + 자체 시험**이다(계획 7절과 동일).

## 2. API 구현 상태 (계획 2절 대비)
| 계약 항목 | 상태 | 비고 |
|---|---|---|
| `set_prec(bits)`, `get_prec()`, 기본 128 | 구현됨 | `bits`는 1 이상의 int. `bool`·`float`은 `TypeError`, 0 이하는 `ValueError` |
| `DI(lo, hi=None)`, int/Fraction | 구현됨 | lo>hi → `ValueError`(반올림 *전* 정확한 비교). lo는 내림, hi는 올림. 점 구간도 같은 규칙(예: `DI(Fraction(1,3))`은 폭이 0이 아닌 구간) |
| `lo_q`, `hi_q` (정확한 Fraction) | 구현됨 | |
| `+ - * /` (DI끼리, DI와 int/Fraction, 반사형 포함), 단항 `-` | 구현됨 | int/Fraction은 `DI(x)`로 바꿔 쓰므로, 표현 불가능한 분수는 *바깥쪽으로 넓은* 구간이 되어 **포함 계약은 유지**된다 |
| `sqrt()` | 구현됨 | 하한<0 → `ValueError`(0을 포함하는 `[0,4]`는 허용). 완전제곱이면 정확한 값 |
| `sqr()` | 구현됨 | 0을 걸치면 하한 정확히 0 |
| `__pow__` (n ≥ 0 정수) | 구현됨 | n=0 → [1,1](0⁰=1 규약, 아래 6절에 명시). n<0 → `ValueError`. 비정수 n → `NotImplemented`→`TypeError` |
| `contains(q)` | 구현됨 | int/Fraction만(그 외 `TypeError`) |
| `width_q()` | 구현됨 | |
| `hull(other)`, `intersect(other)` | 구현됨 | `intersect`는 비면 `None`(엄밀 비교). 한 점에서 닿으면 점 구간 |
| 나눗셈에서 제수가 0을 포함 → `ZeroDivisionError` | 구현됨 | 끝점이 0인 경우 포함. 0이 아닌 아주 작은 수는 내림해도 0이 되지 않음(시험함) |
| 끝점 가수 ≤ `get_prec()` 비트 | 구현됨 | 정밀도를 만든 *뒤에* 낮춰도 지켜지도록 `hull`/`intersect`/`-`도 같은 바깥쪽 반올림을 거친다 |
| (계약에 없는 추가) 표준형, `__eq__`/`__hash__`, `__repr__` | 추가함 | 가수의 꼬리 0 비트를 지수로 옮겨 같은 값은 같은 표현. 계약 동작에는 영향 없음 |

계약에 *명시되지 않아* 내가 정한 해석(검사기 작성자와 다를 수 있음 — 최종 실행에서 어긋나면 계약 문서 쪽을 고쳐야 한다):
1. `float`, numpy 수는 거부(`TypeError`). 계약이 int/Fraction만 말함.
2. `x ** 0`은 x가 0을 포함해도 [1,1].
3. `hull`/`intersect`/`contains`의 상대 인자에 int/Fraction도 허용(`hull`·`intersect`는 `DI(x)`로 바꿈).
4. `intersect`에서 정밀도를 낮춘 경우 결과는 정확한 교집합을 *포함*하되 바깥쪽 반올림 때문에 약간 넓을 수 있다.

## 3. 반올림 방향 근거 요약 (코드 검토용; 상세는 `dyad.py` 각 함수 머리 주석)
정수 도구 두 개가 전부다. `_dn(m,e,p)`: 값 m·2^e 이하인 p비트 값 중 최대(내림). `_up`: 이상인 최소(올림).
- `>>`는 파이썬에서 음수에서도 −∞ 쪽 내림이므로 `_dn`은 `m >> s`. `_up`은 `-((-m) >> s)` = 올림. 음수에서도 맞다. 올림으로 가수가 2^p가 되면(p+1비트) 2의 거듭제곱이라 `_canon`이 정확히 줄인다.
- **덧셈·뺄셈**: [a,b]+[c,d]=[a+c,b+d], [a,b]−[c,d]=[a−d,b−c]. 정확한 정수 합의 하한엔 `_dn`, 상한엔 `_up`.
- **곱셈**: 쌍선형이므로 극값은 네 꼭짓점 곱. 정확한 정수 곱 네 개의 최소에 `_dn`, 최대에 `_up`(정확한 비교, 반올림 전).
- **나눗셈**: 제수 y>0이면 최소 = (lo_x≥0 ? lo_x/hi_y : lo_x/lo_y), 최대 = (hi_x≥0 ? hi_x/lo_y : hi_x/hi_y). 정수 몫 `floor(a·2^k / b)`는 정확한 몫 이하(하한용), 나머지가 있으면 +1이 이상(상한용); k는 몫이 p+1비트 이상이 되게 잡아, 정수 격자가 p비트 격자보다 촘촘하다 → 내림의 내림이 정확한 값의 p비트 내림과 같다(불필요하게 넓어지지 않음). y<0이면 x/y = −(x/(−y)) (부호 반전은 정확).
- **sqrt**: 증가함수. `isqrt(m·4^k)`가 정확한 √ 이하의 정수 근사, 완전제곱이 아니면 +1이 이상의 정수 근사. 하한에 전자의 `_dn`, 상한에 후자의 `_up`. 지수가 홀수면 가수를 1비트 밀어 짝수로 맞춘다.
- **거듭제곱**: 끝점의 n제곱을 정확한 정수로 구한 뒤 한 번 반올림. 홀수 n·lo≥0은 증가, 짝수 n·hi≤0은 감소(끝점 교환), 짝수 n이 0을 걸치면 하한 0·상한은 두 끝점 거듭제곱 중 큰 값의 `_up`.
- **생성자의 Fraction → p비트**: 정수 나눗셈으로 몫과 나머지를 구해 내림/올림(음수는 크기에서 올림/내림을 교차 적용).

- 각 반올림 방향 논증은 위 3절 및 코드 주석의 사람이 읽는 논증이며 형식 증명이 아니다.
- **전역 정밀도**: `set_prec`는 모듈 전역 상태다. 다중 스레드·다중 호출자가 다른 정밀도를 쓰면 서로 영향을 준다(시험하지 않음).
- **자원 한계**: 지수 범위 제한이 없다. 지수 차이가 매우 큰 두 수의 덧셈(예: 2^(10^7) + 1)은 정확한 정수로 더하므로 시간·메모리가 지수 차이에 비례한다(2^±2000은 시험·문제없음, 그 이상은 미측정). `x ** n`도 n이 매우 크면 비용이 크다.
- **속도**: 위 값은 이 PC·파이썬 3.12.7·1세션 한정. 파이썬 속도가 R2 이후에 병목이 될지는 UNKNOWN.
- **계산 범위 밖**: ODE 적분, 의존성 억제(Lohner 등)는 R1~R3. 연쇄 연산의 부풀음은 측정하지 않았다.
- 선행 구현 조사는 이 단계에 포함되지 않았다(별도 세션 담당).
- 이 세션은 Git 커밋·푸시를 하지 않았다. 새 파일은 모두 untracked.

## 7. 자기반박
- 내 시험이 통과해도 남는 반례: 정답표와 구현이 *같은 오해*(예: 음수 올림 정의)를 공유하면 둘 다 틀릴 수 있다. 손 계산 사례와 변이 시험으로 줄였지만 없앤 것은 아니다. 독립 검사기가 필요한 이유다.
- 가장 약한 가정: "곱셈·나눗셈의 극값이 꼭짓점에서 생긴다"(쌍선형·단조) — 수학적으로 표준이며, 무작위 시험이 4꼭짓점 brute force와 일치함을 확인했지만 완전 증명은 하지 않았다.
