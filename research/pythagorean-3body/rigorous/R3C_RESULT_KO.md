## 1. 쉬운 설명 (비유와 실제 의미를 구분해서 읽을 것)

**하려던 것.** R2의 반듯한 그릇(축에 나란한 상자) 대신 **반죽 방향을 따라 기우는 그릇**으로 피타고라스 삼체 문제를 t=0부터 20까지 엄밀하게 따라가 보고, 그릇이 얼마나 커지는지 쟀다.
- 비유: 반죽 = 진짜 가능한 상태들이 모여 있는 범위. 그릇 = 그 반죽을 "반드시" 담고 있다고 증명된 용기. 그릇의 빈 공간 = 군더더기.
- 실제: 그릇 = 집합 { c + B·r : r ∈ R } (중심 점 c 12개 수, 축 행렬 B 12×12, 축마다 폭 R 12개). "반죽"은 걸음마다 넣은 오차(반올림·테일러 나머지)가 진짜 흐름을 따라 퍼졌을 때 차지할 범위의 추정이다(계기판 M3; **엄밀값이 아니다**). 시작점이 한 점이므로 진짜 해는 한 점이고, 반죽은 "계산 과정이 어쩔 수 없이 만든 불확실성"의 크기다.

**결과 1 — 첫 근접 조우 전까지는 그릇이 반죽에 거의 꼭 맞았다.** 계기판(그릇 폭 ÷ 반죽 추정 폭)이 t=0.5, 1.0, 1.5에서 10^0.05, 10^0.17, 10^0.23(벡터 정의)였다. 그 구간에서 빈 공간은 2배 안팎이다(추정 계기판 기준).

**결과 2 — 첫 근접 조우(t=1.8793, 별 2·3이 0.0097까지 접근, 상대 속도 43)에서 그릇이 터졌다.** 128비트 실행은 t=1.876725에서 폭이 1을 넘었다(중단 (a)). 반듯한 그릇(R2, t=6.97)보다 일찍이다.

**왜?** 측정 기록에서 바로 보였다(§9-1).
- 비유: 이 방법은 매 걸음 그릇의 축 이름표를 다시 붙인다. 계획 문언의 규칙은 "이번 걸음에 가장 길게 늘어나는 축을 1번으로"였다. 조우 중에는 늘어나는 방향이 빠르게 바뀌어서 1번 축이 거의 매 걸음 바뀌었고, 그때마다 반죽이 가장 많이 담긴 칸이 맨 뒤 번호로 밀려났다. 이 방법의 그릇 갱신 방식은 뒤 번호 칸의 반죽을 앞 번호의 모든 칸에도 "혹시 몰라" 덜어 담는다. 그래서 빈 공간이 걸음마다 약 2~2.5배씩 불어나 0.02 시간 동안 30자릿수가 커졌다.
- 실제: 새 이름표 R′ = C·R + (새 오차), C ≈ (QR 분해의 위삼각 R 인수)·(피벗 순열). 위삼각이므로 |C_ij|·R_j (j > i)가 R_i에 더해진다(wrapping). 큰 R_j가 뒤쪽 j로 가면 앞쪽 모든 i가 그만큼 커진다. 조우 직전 104걸음 중 51걸음에서 피벗 순열이 항등이 아니었다(조우 전 t<1.8에서는 215걸음 중 17걸음).

**결과 3 — 계획 밖 진단.** 축 번호 규칙만 "늘어나는 정도 × 그 칸에 담긴 반죽 폭"(Lohner 1987이 권하는 형태)으로 바꾸고 나머지는 똑같이 돌렸다. 같은 조우를 폭 10⁻²⁹ 수준으로 통과했고, R2가 터진 t≈7을 10⁻²⁶ 수준으로 지났다. 따라서 이번 터짐은 "기울인 그릇" 생각 자체보다 **축 번호 규칙 문언**의 영향이 크다는 근거가 있다(같은 조건 1회 비교. 증명 아님).

**결과 4 — 정밀도.** 256비트 실행은 계획의 보폭 규칙(허용치 tol = 2^(−정밀도+16)에 비례)으로 보폭이 2⁻¹²~2⁻¹³이라 걸음이 매우 많았다. 3시간 상한 전인 t=1.3887(7,304걸음, 2시간 11분)에서 설계자 지시로 조율 쪽이 중단했다(로컬 CPU 확보; 계획 중단 조건이 아님, §9-4). 그때까지 폭은 10⁻⁷²·⁰ 수준이었고 계기판 비율은 약 1이었다. 같은 속도로 3시간을 다 썼더라도 t≈1.75 안팎이었을 것이라 첫 조우(1.88)에는 닿지 못했을 것으로 본다(추정). 그래서 "R3c에서 정밀도를 높이면 도움이 되는가"는 이번에 확인하지 못했다.

**결론의 강도.** 계획 6절 판정 규칙(t∈[10,20] 성장률로 t=60 외삽)은 계획대로 한 두 실행 모두 t=20에 닿지 못해 **적용할 수 없었다(UNRESOLVED)**. "R3c 주 경로 확정" 조건은 **충족되지 않았다**. 다음 선택은 설계자 판단 사항이다(§12).

## 3. 구현 — `lohner_step.py`

계약(계획 7절) API: `lohner_init`, `lohner_step(system, state, h, order) -> (state_new, info)`, `enclosure_box`, `state.c/B/R/t`, info 키 `h_used`, `width_remainder`, `apriori_iters`, `injected_width`(정확히 이 4개). system은 R1의 `make_*` 그대로.

### 3.1 한 걸음의 엄밀성 근거 (코드 머리 주석 (0)~(7)의 요약)
1. **(0)** 귀납 가정 x(t_k) ∈ X_k. X̂ := hull(외접 상자, c)는 X_k와 c를 포함하는 볼록 상자.
2. **(1) 경로 상자 P:** R1의 Picard 검사(`taylor_step._apriori_enclosure`, 수정 없이 호출)를 X̂에 적용 → X̂의 모든 점에서 출발한 해가 [0,h] 동안 P 안.
3. **(1′) 변분 상자 W:** V = Dφ는 V′ = Df(x)·V, V(0)=I. I + [0,h]·([Df](P)·W) ⊆ W이면 [0,h] 동안 V ∈ W (선형 피카르 논증; [Df](P)는 아래 자동미분의 1차 계수에서 얻음). 실패하면 h를 반으로 줄여 (1)부터.
4. **(2)** φ_h(c) ∈ T(c) + Z, T(c) = Σ_{m≤20} [x_[m]](c)·h^m, Z = h²¹·[x_[21]](P) (성분별 라그랑주 나머지, R1과 같은 논증).
5. **(3) [J] ⊇ {Dφ_h(y) : y ∈ X̂}:** V(τ;y) = Σ Dx_[m](y)τ^m 이고 시각 s에서 V의 m차 계수는 Dx_[m](x(s))·V(s) (흐름 성질 + 연쇄법칙). 성분별 라그랑주 나머지로
   [J] = Σ_{m≤20} [Dx_[m]](X̂)·h^m + h²¹·([Dx_[21]](P)·W).
   Dx_[m]은 R1 계수 재귀(`system.coeffs`)를 **그대로** 호출하면서 입력만 12방향 전진 자동미분 수(`_GD`: 값 구간 + 미분 구간 12개)로 바꿔 얻는다(재귀를 다시 쓰지 않음).
   평균값 정리(적분형): 선분 c→x가 X̂ 안이므로 φ_h(x) − φ_h(c) = J*·(x − c), J* ∈ [J]. **[J]를 X̂ 전체에서 계산했기 때문에 이 형태가 X_k 전체에서 성립한다.**
6. **(4)** c′ = (T+Z의 정확한 중점)의 현재 정밀도 내림 → c′ ∈ T+Z.
7. **(5) 새 틀(근사 허용):** A = mid([J])·B (배정밀도), 열 피벗 QR(Householder) → B′ = Q (부동소수는 이진 분수이므로 Fraction으로 정확히 옮김). **B′⁻¹은 Fraction 가우스–조르당으로 정확히** 구한 뒤 성분별 바깥 반올림 구간으로 감쌈.
8. **(6)** r′ = B′⁻¹(φ_h(x) − c′) = (B′⁻¹J*B)·r + B′⁻¹(φ_h(c) − c′) ∈ ([B′⁻¹]·([J]·B))·R + [B′⁻¹]·(T+Z−c′) =: R′. 따라서 φ_h(x) ∈ {c′ + B′r′ : r′ ∈ R′}.
9. **(7)** 걸음 안쪽 시각 τ의 엄밀 상자(진단·AUX용): 같은 식을 h 대신 τ로.

비엄밀(정확성과 무관, 효율·폭에만 영향)인 부분: QR 분해, 피벗 선택, 보폭 선택, 계기판 M3.

### 3.2 계약 빈칸에 대한 구현 해석 (검사기 작성자와 다를 수 있음)
- K1. `width_remainder`, `injected_width`는 R1 관례대로 **성분별 Fraction 목록**. `apriori_iters` = R1 Picard 검사 횟수(h 축소 전후 합) + 변분 W 검사 횟수.
- K2. `lohner_init`: c = x0의 현재 정밀도 내림, B = I, R_i = DI(x0_i − c_i). x0가 이진 분수면 R = 0.
- K3. state의 c, B, R 끝점이 이진 분수가 아니거나 가수 > 현재 정밀도이면 `ValueError`(결정 A). 반환 직전 새 state도 검사.
- K4. R1의 비공개 이름(`_apriori_enclosure`, `_inflate`, `_subset`, `_System`, `_Singular`)을 import해서 쓴다(수정 없음). 봉인 파일이라 바뀌지 않지만, 공개 API가 아닌 것에 의존한다는 점을 적어 둔다.
- K5. 피벗 = Businger–Golub(매 단계 남은 열 중 잔여 2-노름 최대). 계획 문언 "열 노름 순으로 피벗"의 해석이며 **실행 전에 고정**했다. B′은 53비트 가수(정밀도 ≥ 53일 때 정확; 그 미만이면 내림).
- K6. 계약 밖 선택 인자: `diag=`(진단값), `prep=`(h와 무관한 계산 캐시, 결과 동일함을 시험), `pivot=`(기본 "colnorm"). 4개 인자로 부르면 계약 그대로 동작한다.
- K7. 실패: `LohnerStepError`(RuntimeError 하위) — 메시지에 "singular" / "a priori" / "frame".
- 비용: 피타고라스 한 걸음 단독 약 0.8 s, 그중 약 90%가 두 번의 12방향 자동미분 계수 계산(X̂ 위 20차, P 위 21차)이다(프로파일로 확인). 정확한 역행렬은 무시할 만했다.

- 걸음당 시간은 정밀도와 거의 무관했다(파이썬 객체 비용이 지배). 걸음 수는 보폭 규칙이 정한다: tol이 2^(−prec+16)이고 h ∝ tol^(1/20)이라 256비트의 h는 128비트보다 약 2^(−128/20) ≈ 1/85배다(유도).
- 사전 상자·재시도: 128 계획은 버린 시도가 17%, 진단은 23%(대부분 조우 부근).

## 6. R3-S4 — 기준 궤적 격자 포함 점검 (R2-S1과 같은 규칙)

| 실행 | 걸음 끝(외접) | 경로 상자 P | 위반 | AUX(계획 밖) |
|---|---|---|---|---|
| 128 계획 | 7건 전부 UNDECIDED | **187건 PASS** (폭 log₁₀ −2.05 ~ −1.55) | **0** | 180건 UNDECIDED, 위반 0 |
| 256 계획 | 5건 전부 UNDECIDED | **138건 PASS** (폭 log₁₀ −3.96 ~ −3.51) | **0** | 133건 UNDECIDED, 위반 0 |
| 128w 진단 | 7건 UNDECIDED | 876건 PASS (−2.13 ~ −0.85) | 0 | 869건 UNDECIDED, 위반 0 |

- **S4: 128·256 계획 실행 모두 위반 0** (위반 파일 `r3c_violation_*.json` 없음).
- **검사력은 약하다(R2와 같음).** 판정된 것은 전부 넓은 경로 상자 P(폭 약 0.01~0.1)다. 좁은 상자(걸음 끝 외접, AUX)는 폭이 전부 10⁻¹⁵ 이하라 규칙상 UNDECIDED였다. 기준 궤적의 오차(P3B-0: ≲ 10⁻²⁰ 수준)보다 상자가 좁기 때문이다. 보조로 UNDECIDED 판정에서도 기준값이 상자 안이었는지 기록했다(판정에 쓰지 않음). 128 계획(걸음 끝 7/7, AUX 180/180)과 128w(7/7, 869/869)는 전부 안이었다. **256 계획은 0/5, 0/133 — 전부 밖이었다.** 256비트 상자 폭(약 10⁻⁷²)이 기준 궤적 자체의 오차보다 훨씬 좁기 때문으로 보이며(R2 256비트에서도 같은 현상, R2 보고서 §3), 규칙상 UNDECIDED이고 위반이 아니다. 즉 이 기준 궤적으로는 256비트의 좁은 상자를 판정할 수 없다. (128비트에서 전부 안이었던 것은 그 상자들(10⁻³³~10⁻²⁵)보다 기준 궤적 오차가 작았다는 뜻으로 읽히지만, 판정 규칙 밖의 참고 사항이다.)
- 실행 전 스모크에서 위반 경로를 시험했다: 기준값 성분 하나에 +1을 더하면 S4_VIOLATION으로 멈추고 최소 반례 파일을 썼다(임시 폴더, R3c 결과 아님).

## 8. 계획 밖 진단 — 축 순서 규칙만 바꾸기 (`--pivot width`)

- **왜 했나:** 128비트 계획 실행이 터진 직후, 걸음 기록에서 피벗 순열이 매 걸음 바뀌는 것을 보았다(§9-1). "터짐이 축 순서 규칙 탓인가, 기울인 상자 방법 자체의 한계인가"를 가르는 가장 싼 실험이 이 규칙 하나만 바꾼 실행이었다. 자체 시험 단계(케플러 원 궤도, §9-2 #2)에서도 같은 차이의 신호가 있었다.
- **무엇을 바꿨나:** QR의 피벗 선택 기준을 "잔여 열 2-노름" → "잔여 열 2-노름 × 그 열에 해당하는 이름표 폭 R_j"로만 바꿨다. 정확성 논증(§3.1)은 피벗과 무관하므로 엄밀성은 같다. 나머지(차수, 보폭 규칙, 중단 조건, S4·AUX)는 같다.
- **결과(1회):**
  - 같은 시각 비교(두 실행은 486번째 걸음(t=1.87672)까지 보폭과 버린 시도 수가 완전히 같았다; 487번째부터 갈림): 폭 log₁₀ — t=1.85: −30.64 대 −30.53, t=1.87: −26.30 대 −29.83, t=1.875: −15.85 대 −29.38, t=1.8767: **−2.76 대 −29.12**.
  - 피벗 순열이 항등이 아닌 걸음: t∈[1.87, 1.8767]에서 계획 51/104 대 진단 4/104.
  - 진단은 t=8.760639까지 4,494걸음을 갔고(구현자가 중지), 근접 조우 5개를 지났다. R2가 터진 t≈7에서 폭 10⁻²⁵·⁷. S4·AUX 위반 0.
- **이 결과로 말할 수 있는 것과 없는 것:**
  - 있다: 이번 128비트 터짐의 직접 원인은 "축 순서 규칙 문언"이라는 강한 근거(같은 입력, 규칙 하나 차이, 26자릿수 차이).
  - 없다: 진단 규칙으로 t=20, t=60까지 갈 수 있다는 것. t=8.76 이후(특히 d=4.1×10⁻⁴인 t=15.83 조우)는 측정하지 않았다. 계획 판정에 쓰지 않는다.

## 9. 실행 중 문제와 대응 (고치기 전에 원인 기록)

### 9-1. 128비트 계획 실행이 첫 근접 조우에서 터짐 (측정 결과이며 계획 8절의 "실패"가 아님)
1. **무슨 일:** t=1.85~1.8767 사이 폭이 10⁻³⁰·⁶ → 10⁺²·⁴. 마지막 걸음(h=2⁻²⁰, 사전 상자가 h를 줄임)에서 폭 > 1. 주입 오차(나머지+반올림)는 계속 10⁻³⁶ 안팎이었고, 틀의 직교성 결함은 최대 1.3×10⁻¹⁵, 계산 예외·위반은 없었다.
2. **왜(확인한 증거):** 걸음당 폭이 약 2~2.5배씩 커졌고(h=2⁻¹⁵에서 0.3~0.4자릿수/걸음), 같은 구간에서 피벗 순열이 104걸음 중 51걸음 항등이 아니었다(열 0과 열 11이 번갈아 1번 자리). 같은 입력에서 피벗 기준만 바꾼 진단은 이 구간 증가가 3자릿수 미만이었다(§8). 대안 가설 — (a) [J]의 구간 폭(의존성) 탓: [J] 폭 × 이름표 폭 항은 폭의 제곱 규모라 이 구간에서 무시할 만했다(예: i=450에서 폭 10⁻¹³·⁷, [J] 폭 10⁻¹¹·⁶ → 곱 10⁻²⁵·³). (b) 틀의 특이화: 직교성 결함 10⁻¹⁵, 정확한 역행렬 사용 → 아니다. (c) 나머지/반올림: 주입 폭 10⁻³⁶ → 아니다. 그래서 피벗 문언에 따른 wrapping이 가장 유력하다(진단 실행이 직접 지지).
3. **왜 사전에 못 잡았나:** 자체 시험에 근접 조우처럼 "늘어나는 방향이 걸음마다 빠르게 바뀌는" 경우가 없었다. 신호는 있었다: 케플러 원 궤도 시험에서 이름표가 지수적으로 커졌고 그 지수가 colnorm 약 1.05/시간, width 약 0.58/시간이었다(§9-2 #2, 실행 전 진단). **나는 그 차이를 보고도 계획 문언을 따르기로 하고 실행했다.** 실행 전에 설계자에게 "피벗 문언을 이대로 갈지" 묻는 선택지가 있었고, 그렇게 했다면 3시간 실행 하나를 아꼈을 수 있다.
4. **어디서 또 일어나나:** 같은 규칙이면 모든 깊은 조우(t≤20에서 d<0.01인 조우가 3개: 1.88, 8.76, 15.83)에서 같은 일이 예상된다(추정). 256비트도 같은 규칙이다.
5. **수정의 부작용:** 고치지 않았다(계획 규칙). 피벗 규칙을 바꾸려면 새 계획·봉인이 필요하다(설계자 판단).
6. **입증:** §8의 진단 1회. 독립 확인 없음.

### 9-3. 진단 실행의 자원 상한 위반 (구현자 실수)
- **무슨 일:** 진단 실행(128w)을 계획 실행과 같은 기본 wall 상한 3시간으로 띄웠다. 계획 9절은 "피타고라스 실행은 128·256비트 각각 3시간, **그 밖의 실행은 60분**"이다. 진단 실행은 계획의 두 실행이 아니므로 60분 상한이 맞는 읽기다. 실행 91.5분째(16:31)에 이를 알아차리고 프로세스를 강제 종료했다.
- **왜:** 실행 스크립트의 기본값을 그대로 썼고, 계획 9절을 진단 실행에 다시 대조하지 않았다.
- **영향:** 비용은 이 PC의 CPU 시간뿐이다(서버·요금 없음). 계획 실행 두 개와 CPU를 나눠 써서 256비트 실행의 걸음 속도에 영향을 주었을 수 있다(정량화하지 않음). 진단 결과는 종료 직전까지 줄 단위로 기록된 것만 쓴다. 최종 요약 파일은 프로세스가 쓰지 못해 없고, 대신 구현자가 기록에서 만든 `r3c_stopnote_128w.json`이 있다(그렇게 만들었다고 파일 안에 적음). 걸음 기록 4,494줄과 자코비안 기록 4,494줄이 일치함을 확인했다.
- **60분 시점까지의 결과만으로도** 진단 목적(첫 조우 비교)은 달성됐다(첫 조우는 실행 10분 안에 지남).

### 9-4. 256비트 계획 실행 중단 — 설계자 지시 (STOPPED_BY_DESIGNER_LOCAL_CPU)
1. **무슨 일:** 시작 7,860초 뒤(17:01:32), t = 1.388671875(7,304걸음)에서 프로세스가 끝났다. 마지막 걸음 기록 쓰기 17:01:31.79, 셸 종료 기록 17:01:32.79(`exit=127`). final 파일 없음, stderr 0바이트. 계획 중단 조건 (a)–(d)는 어느 것도 해당하지 않았다(폭 10⁻⁷², h = 2⁻¹³, t < 20, wall 상한 10,800초 전).
2. **원인 (조율 세션의 통지):** 실행이 끝난 뒤 조율 세션이 크로스 세션 메시지로 "**설계자 지시로 조율 쪽에서 PID 68620을 약 17:01 KST에 중단했다, 목적은 로컬 CPU 확보, 다시 실행하지 말 것(앞으로 무거운 실행은 GCP)**"이라고 알려 왔다. 그래서 중단 사유를 `STOPPED_BY_DESIGNER_LOCAL_CPU`로 기록했다. 이 사유는 통지에 근거한 것이고, 내가 독립적으로 확인한 것은 아래 기록상의 사실뿐이다.
   - 통지 전 내가 확인했던 것(통지와 합치): 그 시각 Windows 응용 프로그램·시스템 로그에 python 오류 보고가 없고 재부팅도 없음, `exit=127`은 내가 Stop-Process로 끝낸 128w와 같은 값, 내 16:31 종료 명령은 `--pivot width` PID 73640만 대상(직후 68620 살아 있음 확인). 통지 전에는 원인을 몰라 `EXTERNAL_TERMINATION_UNKNOWN`으로 기록했고, 통지를 받은 뒤 바꿨다.
   - 수치 차이 한 가지: 통지의 "마지막 기록 t=1.388184, step 7300, wall 7856 s"는 진행 로그(25걸음마다 한 줄)의 마지막 줄이다. 줄 단위 걸음 기록은 그 뒤 4걸음 더 있다(7,304걸음, t = 711/512 = 1.388671875, 7,860 s). 이 보고서는 걸음 기록 값을 쓴다.
3. **기록 보존:** 실행 요약(final)은 끝날 때 한 번 쓰는 구조라 강제 종료에는 남지 않는다. 줄 단위 flush 덕분에 걸음·격자·자코비안 기록(각 7,304줄, 서로 일치)은 남았다. 정지 기록 `r3c_stopnote_256.json`은 구현자가 이 기록에서 만든 것이며 파일 안에 그렇게 적었다.
4. **영향:** 256비트 결과는 t ≤ 1.3887 범위뿐이다. 같은 속도로 3시간을 다 썼어도 t≈1.75 안팎(첫 조우 1.88 전)이었을 것으로 추정되므로, 판정·조우 비교에 대한 정보 손실은 작다고 본다(추정).
5. **대응:** 지시대로 다시 실행하지 않았다. 그때까지의 기록만으로 분석·보고서를 마무리했다.

## 13. 자기반박 · 파급효과
