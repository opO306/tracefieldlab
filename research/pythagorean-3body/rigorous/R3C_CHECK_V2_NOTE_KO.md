## 1. 쉬운 설명

- 비유(실제와 구분): 택배 **검수원**(검사기)이 창고(구현)에 시험용 상자를 넣어 본다. 창고 규정은 "치수는 2의 거듭제곱 눈금(1/2, 1/4, 1/8 …)으로만 적는다"인데, v1 검수원은 피타고라스 시험 상자 중심을 **1/1000 눈금자**로 재서 넣었다. 창고는 규정 밖이라 접수를 거부했고, 검수원은 그 10개 상자를 시험하지 못했다(틀렸다는 뜻이 아니라 "못 해 봤다"는 뜻).
- 실제: 구현은 `state.c`의 숫자가 이진 분수(분모가 2의 거듭제곱)이고 가수 비트 수가 실행 정밀도(128 또는 256) 이하여야 한다. v1은 `c`에 `…/1099511627776000`(=2⁴⁰×1000) 같은 분모를 넣었다. 5³ 인자 때문에 이진 분수가 아니다.
- v2는 눈금자를 2⁻⁵⁰ 칸으로 바꿔 같은 위치에 (오차 ≤ 2⁻⁵¹ ≈ 4×10⁻¹⁶) 상자를 놓는다. 또 검수원이 상자를 넣기 직전에 **규격 검사기**를 한 번 돌려, 자기가 넣는 상자가 규정 안인지 스스로 확인한다. 규정 밖이면 구현 탓이 아니라 검수원 자신의 오류로 멈춘다.
- 이 논리의 허점도 확인했다: v1의 자기시험 때 **참조 구현이 규정을 검사하지 않아** 분모 1000을 그냥 받아 줬다. 그래서 검수원의 결함이 자기시험에서 안 드러났다. v2의 자기시험은 참조 구현·가짜 구현을 "규정 엄수 래퍼"(§3)로 감싸 실제 구현처럼 거부하게 만들었다.

## 3. 자기시험 ① — v1 재현 (원인이 맞는지)

`run_r3c_v2_selftest.py`는 `_fake_r3c_core`의 참조 구현·가짜 구현을 **계약 엄수 래퍼**로 감싼다: `lohner_step`에 들어온 state의 `c`·`B`·`R` 끝점이 이진 분수(가수 ≤ `dyad.get_prec()`)가 아니면 실제 구현이 낸 것과 같은 문구의 `ValueError`를 던진다. (`lohner_init`은 비이진 `x0`가 오면 가까운 이진 중심 + 오차를 덮는 `R`로 바꿔 준다. X2의 `x0`에 9/10이 있어서다. 실제 구현이 이를 어떻게 하는지는 **모른다** — 조율 쪽 보고에서 X2가 REFUSED로 나오지 않았다는 점만 근거다.) 가짜 구현 파일은 수정하지 않았고 래퍼는 실행기가 자동 생성한다.

| 실행 | 결과 |
|---|---|
| v1 × 래퍼 씌운 참조 구현, `--only S2,X4` (53초) | **S2: PASS 504, REFUSED 8 / X4: PASS 200, REFUSED 2 / C·X1: PASS, 위반 0.** 거부된 건 nbody 상자 전부(S2 box12–19, X4 box04–05) |
| 예외 문구 | `ValueError: state entry 1100430930827161/1099511627776000 is not a dyadic with <= 128 mantissa bits (R0 decision A: one precision per run)` (box18) — 과제 설명에 인용된 GCP 오류와 **같은 값·같은 문구** |

→ 원인 가설(비이진 `c` 주입)이 재현으로 **확인**됐다. 일치의 의미를 정직하게 적으면: 예외 *문구*는 래퍼를 만들 때 과제 설명에서 가져온 것이라 일치가 증거가 아니다. 증거는 *값*이다 — 거부된 값 `1100430930827161/1099511627776000`은 seed 20261011과 v1의 `start_center`만으로 정해지며 래퍼는 입력을 검사만 할 뿐 값을 만들 수 없는데, 그 값이 GCP 실제 구현의 오류 값과 일치했다. 그리고 거부된 건수(S2 8 + X4 2)도 보고와 같고, 래퍼 재현에서 그 10건은 nbody 상자 전부다(과제 설명에서 상자 번호는 받지 못했다). 거부된 10건의 분모는 모두 2ᵏ×1000 꼴이다(예: 2⁴⁰×1000, 2³⁸×1000, 2³⁴×1000). 아직 확인하지 못한 것: 실제 구현이 이 10건 말고도 다른 이유로 거부하는 입력이 있는지(아래 §6).

## 6. 한계와 아직 모르는 것

- **실제 `lohner_step.py`에는 실행하지 않았다.** v2가 S2 8건·X4 2건을 실제 구현에서 시험 가능하게 만들었는지는 **미확인**이다. 확인한 것은 "계약 엄수 래퍼를 씌운 참조 구현에서 REFUSED 0"까지다. 실제 구현은 이 10건을 다른 이유(사전 상자 실패, 다른 입력 검증)로 거부할 수 있다. 그러면 예외 문구를 보고 구현 결함인지 계약 해석 차이인지 먼저 구분한다(계획 8절).
- **래퍼는 내가 아는 규칙 하나만 흉내 낸다**: 입력 state의 `c`·`B`·`R` 끝점이 이진 분수이고 가수 ≤ 현재 정밀도. 실제 구현이 이 밖에 무엇을 검증하는지(출력 state, 보폭 `h`의 형식, 차수 상한 등)는 모른다.
- **비이진 `x0`의 처리(X2의 9/10)는 모른다.** 래퍼는 "가까운 이진 중심 + 오차를 덮는 R"로 가정했다. 과제 설명에 따르면 GCP 실행에서 REFUSED는 S2 8 + X4 2뿐이었으므로 X2는 통과한 것으로 보이지만, 나는 그 결과 파일을 직접 보지 않았다. 만약 X2가 `lohner_init`에서 거부된다면 v2의 수정 범위 밖이다(`x0`를 이진 값으로 바꾸면 시험 성격이 달라지므로 조율 쪽 판단).
- **S2의 nbody 10건은 v1 × 실제 구현에서 아직 한 번도 시험된 적이 없다.** 따라서 v2에서 점이 ≤ 4×10⁻¹⁶ 옮겨진 것을 v1 결과와 직접 비교할 대상이 없다. harmonic·kepler 상자는 v1과 비트 단위로 같은 입력이다(단위 시험).
- 감사 장치는 `run_s2`에서 주입하는 시작 집합(S2·X4)만 본다. S1·X2·X3는 `lohner_init(x0)`만 쓰고 `state`를 직접 쓰지 않는다.
- 감사가 실패하면 S2만이 아니라 검사 전체가 CHECKER_ERROR(종료 코드 3)로 멈춘다(검사기 버그를 구현 결과와 섞지 않으려는 설계).
- 적발률은 **내가 만든 결함 11종**에 대한 것이며 미지의 결함에 대한 보증이 아니다. `qt_inverse` 미적발은 v1 한계 그대로다. 같은 seed 한 번씩만 돌렸다(다른 seed 반복 없음). 포함만 시험하며 헐렁함(상자 폭)은 판정하지 않는다.
- `ref_cache.pkl`은 입력(시작점, `h_used`)이 같을 때만 재사용된다. 구현이 `h_used`를 줄이면 그 사례는 새로 계산된다(시간만 더 든다). 의심스러우면 지우고 다시 돌리면 같은 결과가 나온다.

## 7. 자기반박 · 파급효과 · 증거

> **자기반박.** v2가 틀렸다면 어디서 먼저 깨지는가? (1) "2⁻⁵⁰ 반올림이 시험을 약하게 했다" — 15개 구현 × 8개 기준에서 위반·시도 수가 v1과 모두 같았으나, 이는 **내가 만든 15개**에 대한 관측이다. (2) "재현이 순환논리다" — 래퍼의 예외 문구는 과제 설명에서 가져왔으므로 문구 일치는 증거가 아니다. 증거는 seed와 v1 코드만으로 결정되는 *값*이 실제 오류 값과 일치한 것이다(§3). (3) "래퍼가 실제 구현보다 너그럽거나 엄격하다" — 사실이다, §6 두 번째 항목. 실제 구현 위에서의 결과만이 최종이다. (4) "다른 원인이 같은 10건을 설명할 수 있다" — 대안 가설: 구현이 12차원 상자에서 사전 상자 실패로 거부. 이 경우 오류 문구가 달랐을 것이고(보고된 문구는 이진 분수 검증), 래퍼 재현이 거부 값과 건수(10건, 전부 nbody 상자)를 재현했으므로 비이진 `c`가 가장 유력하다. 다만 그것이 *유일한* 거부 원인임은 아직 모른다.
>
> **파급효과.** 새 파일만 만들었다. v1 검사기·계획·봉인·`dyad.py`·`taylor_step.py`·구현 파일은 수정하지 않았다. v1 × 실제 구현의 기존 4회 결과(위반 0, S2 8 + X4 2 미시험)는 그대로 유효하며, v2 결과를 거기에 합쳐 해석하는 것은 조율 쪽 판단이다. 판정 기준(위반 0)은 바꾸지 않았다.
>
> **증거 수준.** 확인한 것: v1 해시 불변, 원인 재현(값 일치), v1·v2 코드 차이(추가 59줄·바뀐 줄 5개), 단위 시험 768개, 15개 구현 × 8개 기준의 v1 대조 차이 0, 참조 구현 오탐 0, 필수 6/6 적발. 추정인 것: 실제 구현이 v2에서 10건을 모두 시험 가능하게 받아들일 것(미확인), 래퍼가 모델링한 계약이 실제 구현의 전부라는 것. 미확인(NOT_TESTED): 검사기 v2 × 실제 구현 전체.
