# Gate FC1 계획 — 계산 핵심부를 C++로 다시 쓰기 (원본과 비트 단위 동일), 2026-10-11

> 상태: 계획(실행 전 봉인). 봉인 해시는 `GATE_FC1_SEAL.json`. 실행 뒤 수정 금지.
> 설계자 승인: "B도 해보자", "원본이랑 B로 쓴 그거랑 잘 분리해서 혹여나 문제 생기지 않게" (2026-10-11).

## 0. 쉬운 설명
- 지금 계산은 **부품 하나 옮길 때마다 서류 작업이 붙는 공장**이다. 부품(128비트 수)은 작은데, 걸음마다 16만 번 옮기고 그때마다 파이썬 처리 비용이 붙는다.
- 이번에 가장 바쁜 공정 하나(테일러 계수 계산, 전체 시간의 약 85%)를 **C++ 기계로 바꾼다.**
- 새 기계는 원본과 **같은 순서로, 같은 반올림으로** 계산해야 한다. 그래서 결과가 원본과 **비트 하나까지 같아야** 합격이다. 숫자가 하나라도 다르면 불합격이다.
- 원본(파이썬)은 그대로 둔다. 새 기계는 **별도 폴더**에 두고, 새 실행 스크립트를 쓸 때만 켜진다.

## 1. 근거 (확인)
- 프로파일링(GCP, 128비트, 120걸음, cProfile): `taylor_step` 계수 계산이 누적 85%. 그중 구간 곱셈(`dyad.DI.__mul__`) 57%, 덧셈 25%. 한 걸음에 구간 곱셈 약 16만 번. 정확한 역행렬은 1% 미만.
- gmpy2 측정: 128비트 정수 곱셈 1.09배, 12×12 정확한 역행렬 2.7배(결과 동일). 전체 효과 10% 미만 추정 → 채택 안 함.
- PyPy 7.3.19: 300걸음 1.35배(100~300걸음 1.63배), 결과는 300걸음 모두 원본과 동일.
- 테일러 차수(같은 코드, t=0~1.8, 128비트): 20차 387초(216걸음, 버린 시도 19), 30차 375초(77걸음, 37), 40차 342초(45걸음, 27). 파이썬에서는 차수 효과 1.1배 남짓. 차수는 FC1 뒤 다시 잰다(이번 범위 아님).

## 2. 범위
**이번에 만드는 것**
1. `fastcore/` 폴더(새로 만듦, `research/pythagorean-3body/fastcore/`)
   - C++17 구현: 이진 분수 구간(DI)과 (값, 기울기) 쌍(_GD)의 연산, N체 테일러 계수 재귀. GMP(`mpz`) 사용 허용.
   - 파이썬 연결: pybind11 또는 CPython C API.
   - 파이썬 어댑터 `fastcore/fast_system.py`: `make_nbody_fast(masses)`가 원본 `taylor_step.make_nbody`와 같은 모양의 system 객체를 돌려준다. `coeffs(X, K)`는 입력이 DI 목록이면 DI 경로, `lohner_step._GD` 목록이면 GD 경로로 C++을 부르고, 결과를 원본 클래스(`dyad.DI`, `lohner_step._GD`) 객체로 돌려준다.
   - 빌드 스크립트, 구현자 자체 시험, `fastcore/README_KO.md`.
2. 새 실행 감싸개 `fastcore/r5_run.py`: `r3c_run`/`r4_run`의 system 생성(`taylor_step.make_nbody`)만 `make_nbody_fast`로 바꾸어 부른다. 나머지(보폭, QR, 정확한 역행렬, 포함 점검)는 원본 파이썬 그대로다.

**하지 않는 것**
- `rigorous/` 아래 어떤 파일도 수정하지 않는다(`dyad.py`, `taylor_step.py`, `lohner_step.py`, `r3c_run.py`, `r4_run.py`, 검사기 등).
- 보폭 규칙·차수·피벗 등 알고리즘 변경 없음. 같은 계산을 빠르게 하는 것만이다.
- QR·역행렬·행렬곱 이식은 이번 범위가 아니다(남은 15%. FC1 결과를 보고 FC2에서 정함).

## 3. 분리 규칙 (설계자 요구: "원본과 B를 잘 분리")
| 항목 | 원본 | FC1 |
|---|---|---|
| 소스 위치 | `rigorous/` | `fastcore/` |
| 원본 import | — | 허용(읽기 전용). 원본은 fastcore를 import하지 않음 |
| 실행 스크립트 | `r3c_run.py`, `r4_run.py` | `fastcore/r5_run.py`만 |
| 결과 폴더·파일 | 기존 폴더 | 새 폴더, 파일 이름에 `fc` 표시. 기존 결과 덮어쓰기 금지 |
| GCP 서버 폴더 | `~/p3b_r3cp/` (R3c′·R4 실행 중) | `~/fastcore_dev/`(개발), `~/fastcore_run/`(실행). **`~/p3b_r3cp/`는 읽기만** |
| 서버 CPU | R3c′·R4 실행 8개 | 개발·시험은 동시에 2코어 이하 |

- 작업 시작 전과 끝에 `GATE_R3C_SEAL.json`, `GATE_R3CP_SEAL.json`, `GATE_R4_SEAL.json`에 있는 파일 해시를 다시 계산해 그대로임을 확인하고 보고서에 적는다.
- 증명에 쓰는 결과는 FC1 합격 전에는 **원본 경로 결과만** 쓴다.

## 4. 합격 기준 (실행 전 고정)
비트 동일 = 모든 구간 끝점의 (가수, 지수) 정수 쌍이 같다. 예외도 같은 종류로 같은 지점에서 난다.

| ID | 시험 | 기준 |
|---|---|---|
| FC-1 | DI 경로: 무작위 상자(폭 0, 10⁻³⁰, 10⁻¹⁰, 10⁻³, 0.1, 영 포함 구간 등) × 정밀도 {96, 112, 128, 144, 160, 192, 256} × 차수 {1, 5, 20, 30, 40}, 질량 (3,4,5)와 무작위 유리수 질량, 체 수 {2, 3}. 각 조합 ≥ 50상자 | 원본 `taylor_step.make_nbody(...).coeffs`와 불일치 0 |
| FC-2 | GD 경로: FC-1과 같은 입력을 `lohner_step._seed`로 감싸 비교 | 불일치 0 |
| FC-3 | 특이: 충돌 배치(거리 구간이 0 포함) 입력에서 원본과 같은 예외(`taylor_step._Singular`) | 불일치 0 |
| FC-4 | 실제 궤적: `r5_run.py --prec 128 --pivot width`로 1,000걸음 이상(첫 근접 조우 t=1.88 통과 포함) 돌려 걸음 기록(`t`, `h_used`, `n_discard`, `wmax`)이 원본 128w 기록과 비교 | 불일치 0 |
| FC-5 | 속도: 같은 서버에서 FC-4 구간의 걸음당 시간 원본 대비 | 측정만(판정 없음). 예상 4~6배(추정: 85% 부분이 30배 빨라질 때 계산값) |
| FC-6 | 독립 검사기(아래 5절)가 만든 차등 시험 | 불일치 0 |

- 하나라도 불일치가 있으면 **불합격**이다. FC1 경로를 증명 실행에 쓰지 않는다.
- 원인을 기록하고 고친 뒤 FC-1~6을 전부 다시 돌린다. 기준은 바꾸지 않는다.

## 5. 역할과 독립성
| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 구현 세션 | `fastcore/` 소스·어댑터·빌드·`r5_run.py`·자체 시험(FC-1~5) | 검사기 파일 읽기 |
| 검사 세션 | 이 계획과 원본 파이썬 소스(오라클)만 보고 `fastcore_check/check_fc1.py` 작성. 원본과 FC1 모듈의 공개 API만 사용. 무작위 + 경계 입력(가수 비트 경계, 지수 극단, 영 근처, 부호 경계, 반올림 동률) 생성 | `fastcore/` C++ 소스 읽기 |
| 조율(이 세션) | 최종 실행(검사기 × 구현), 봉인 해시 확인, 판정 | 구현·검사 코드 작성 |

- 오라클은 원본 파이썬이다. 원본이 틀렸어도 FC1은 원본과 같아야 한다. 원본의 정확성은 R0·R1·R3c′ 검사로 따로 다룬다.

## 6. 환경
- 빌드·시험: GCP 서버(Debian, Python 3.13). 필요한 패키지(`g++`, `libgmp-dev`, `python3-dev`, `pybind11-dev` 등)는 Debian 공식 저장소로 설치한다(설계자 승인 범위). 이 PC(노트북)는 편집만 하고 무거운 빌드·시험은 하지 않는다.
- 서버는 이미 켜져 있다. 새 인스턴스·서버 자료 삭제·Git 커밋/푸시는 금지다.

## 7. 증거 수준
- FC1 합격 = "원본과 비트 단위 동일(시험 범위 안)". 형식 증명이 아니다.
- 비트 동일하면 원본에 대한 기존 검사(R0·R1·R3c′ 검사기)의 결론이 FC1 경로에도 그대로 이어진다. 단, **시험하지 않은 입력에서 다를 가능성은 남는다.** 그래서 증명 실행에 쓸 때도 일정 간격으로 원본 경로와 걸음 기록 대조를 함께 한다(FC2 이후 계획에서 정함).

---
> **자기반박:** (1) 원본의 연산 순서(예: `_GD`의 None 처리, `_sq_conv`의 2배, 정수와 구간의 혼합 연산)를 하나라도 다르게 옮기면 비트가 달라진다. FC-1·2가 이것을 잡는다. (2) 속도 이득이 예상보다 작을 수 있다. 파이썬↔C++ 변환 비용, 남은 15% 때문이다. FC-5로 잰다. (3) 검사기와 구현이 같은 원본을 오라클로 쓰므로, 원본의 버그는 둘 다 못 잡는다. 이것은 의도된 범위다.
>
> **파급효과:** 새 폴더 2개(`fastcore/`, `fastcore_check/`)와 서버 패키지 설치. 원본·봉인·실행 중인 작업은 건드리지 않는다.
>
> **모델 추천:** 구현은 강한 모델(Opus급). 비트 동일 이식은 연산 순서 하나만 달라도 실패하는 세밀한 작업이다. 검사기는 Sonnet급으로 충분하다(오라클이 이미 있는 차등 시험).
