## 0. 쉬운 설명

- 원본 계산에서 시간이 가장 많이 드는 공정(테일러 계수 계산)을 C++ 로 다시 만들었다.
  - **비유**: 같은 작업 지시서를 받은 다른 기계.
  - **실제 의미**: 같은 정수 연산을 같은 순서·같은 방향 반올림으로 하는 C++ 함수.
- 원본과 **비트 하나까지** 같은지 자체 시험으로 확인했다. 시험한 입력에서는 모든 끝점 (가수, 지수)가 같았다(불일치 0).
- 실제 궤적에서도 같았다(FC-4). 2,000걸음(t = 0 → 3.78, 첫 근접 조우 t ≈ 1.88 통과 포함) 동안 걸음 기록이 원본 R3c′ 128w 기록과 걸음마다 같았다.
- 빨라진 정도(FC-5): 같은 서버에서 같은 시각에 돌려 비교하면 걸음당 약 **4.5배**다(원본 1.91초 → FC 0.42초).
  계수 계산 한 번만 놓고 보면 약 9~10배다. 걸음 전체로는 그만큼 빨라지지 않는다. 남은 파이썬 부분(구간 행렬곱, QR, 정확한 역행렬, 포함 검사)이 걸음 시간의 절반 이상을 차지하기 때문이다(§4).
- "비트 동일"은 **시험한 범위 안**의 결론이다. 형식 증명이 아니다(계획 7절).

**빌드**
- 서버 환경: `g++ (Debian 14.2.0-19) 14.2.0`, `-O2 -std=c++17`, GMP 6.3.0, Python 3.13.5, Debian 13.7 (`build_info.txt`, 서버).
- 패키지 `g++`, `libgmp-dev`, `python3-dev` 는 Debian 공식 저장소에서 설치했다. pip 는 쓰지 않았다.

**설계 요점** (자세한 내용과 원본 대응표는 `README_KO.md` §3)
- 끝점 (m, e) 를 GMP mpz / int64 로 나타낸다. 지수 계산마다 넘침을 검사한다.
- **입력 끝점은 받은 그대로** 쓴다. 표준형으로 바꾸지 않는다.
- 원본 함수를 한 줄씩 옮겼다: `_dn`, `_up`, `_canon`, `_addx`, `_mulx`, `_qdn`, `_qup`, `_sqrt_parts`, DI 연산, `_GD` 연산, `_conv`, `_sq_conv`, `_pow_m32_next`, `_div_int`, `make_nbody.coeffs`.
- `_GD` 의 None(정확한 0) 규칙을 그대로 따른다.
- DI/정수/`_GD` 혼합 연산의 파이썬 연산자 분배(`__radd__`, `__rsub__`, `__rmul__`, `__rtruediv__`)도 그대로 따른다.
- 질량 DI 는 원본 `dyad.DI` 로, 호출 시점 정밀도에서 만들어 넘긴다. 원본 coeffs 의 첫 줄과 같은 호출이다.
- 특이 입력이면 원본 `taylor_step._Singular` 를 던진다.
- C++ 이 다루지 못하는 입력에는 대체 경로(fallback)를 쓴다. 예: 원본 클래스가 아닌 원소, 2^26비트를 넘는 지수 차이.
  - C++ 은 계산을 버리고, 어댑터가 **원본 파이썬 coeffs 로 다시 계산**한다.
  - 대체 경로를 쓴 횟수를 `fc_stats` 와 r5_run 메타 파일에 기록한다.
- `fast_system` 을 import 할 때 원본 세 파일의 해시를 FC1 봉인과 비교한다. 다르면 import 를 거부한다. 원본이 다른 폴더에서 import 되어 있어도 거부한다.

  - C++ 계수 계산: 걸음당 약 0.16 s (약 42%)
  - 원본 파이썬: 약 0.22 s (58%). 구간 행렬곱 `_imat_mul`(변분 상자 W 반복, J·B, B⁻¹·JB), `_poly_sum`, Fraction 연산(`_inflate`, `_subset`), 정확한 역행렬로 이루어진다.
- 계획의 예상치는 4~6배(추정)였다. 측정값 4.5배는 그 범위의 아래쪽이다.
- 더 빨라지려면 남은 파이썬 부분을 옮기거나 C++ 연산 자체를 빠르게 해야 한다(§8).

## 5. 과정 기록 (실패·수정 포함)

1. **판 v1** (`fastcore.cpp` `18d9e110…ebd1e`)
   - 스모크(K=0~20, DI·GD)와 축소 시험(FC-0 3,000, FC-1/2/3 축소, FC-X 664)에서 불일치 0.
   - 정식 자체 시험을 시작하고 4분 뒤 **내가 중단**했다. 그때까지 FC-2 30 조합이 진행됐고 모두 불일치 0이었다(`results/selftest_v1/`).

     - 출력 변환 단계에서는 파이썬 코드(`DI._new`)를 부른다. 그동안 입력 객체를 **빌린 참조**로만 들고 있었다.
     - 다른 스레드가 같은 입력 목록을 바꾸면, 이론상 해제된 메모리를 읽을 수 있다. 지금 쓰는 방식은 한 스레드라 일어나지 않는다.
     - 입력 객체를 호출이 끝날 때까지 강한 참조로 붙잡도록 고쳤다(`KeepRefs`). 계산 경로는 바뀌지 않는다.
   - 그래도 규칙대로 v2 로 FC-0~3, FC-X 를 **처음부터 전부** 다시 돌렸다(§3). FC-4/5 는 v2 로만 돌렸다.
2. **시험 도구 수정** (구현 코드가 아님. 둘 다 정식 시험 전)
   - FC-0 생성기: 정밀도 1일 때 음수 지수로 Fraction 을 만들다 오류가 났다 → `max(0, …)` 로 고쳤다.
   - FC-1 `straddle` 등급: 위치 성분이 0 을 걸치지 않았다 → 체 0 의 x 를 0 에 두어 걸치게 고쳤다.
3. 원본과의 불일치는 v1·v2 를 통틀어 **한 번도 나오지 않았다.** 따라서 기록할 최소 반례가 없다.
